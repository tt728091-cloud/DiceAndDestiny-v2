Zero-context implementation + operations guide

Train one policy to play either character.

Use this page when two combatants—possibly both brand new and different from each other—are ready for real-authority machine learning. Current repository truth

What the accepted system does today

Treat the repository as the source of truth. Commit IDs here are orientation points, not permission to ignore later changes. A future context must inspect the actual branch and working tree before editing.

01 · AUTHORITY

Rules stay in Go

The model receives a viewer-safe snapshot and the authority’s complete legal-command candidates. It selects an index; the original command is validated and applied by the real Go authority.

02 · TRAINING

Maskable PPO

Four persistent environments feed a shared candidate-scoring policy. Gameplay is stepped sequentially through DummyVecEnv; only the learner changes, while opponents are random, heuristic, or frozen checkpoints.

03 · RUNTIME

Frozen Go inference

Phase 3 exports reviewed actor tensors to JSON and runs deterministic inference in Go. The accepted Blade Warden artifact remains a separate, version-locked baseline.

Target behavior

“Can play either character” has four distinct roles

Let Character X and Character Y be different combatant definition IDs. One shared checkpoint must learn all four role cells below. Training only X in Seat A and Y in Seat B is insufficient: it entangles character strength, seat effects, and learned behavior.

Role AShared learner controls Character X in Seat A; Character Y is the opponent in Seat B.
Role BShared learner controls Character X in Seat B; Character Y is the opponent in Seat A.
Role CShared learner controls Character Y in Seat A; Character X is the opponent in Seat B.
Role DShared learner controls Character Y in Seat B; Character X is the opponent in Seat A.
Required deliverable: a model set means at least three independently trained shared-policy seeds. Every final checkpoint must accept either character’s viewer-safe observation and legal candidates. Two specialized models—one that only plays X and another that only plays Y—do not satisfy this handoff unless the owner explicitly changes the goal.

Balanced scheduling contract

  • Character identity is sampled independently from seat identity.
  • All four learner role cells receive approximately equal episodes and decisions.
  • Held-out evaluation reports each role cell separately before aggregating.
  • Episode seeds are recorded and disjoint between training and evaluation.
  • A shared checkpoint can be loaded into two independent instances simultaneously.
  • Evaluation can also load two different shared checkpoints and swap assignments.

Implementation specification

Generalize the pilot without moving rules out of the authority

The future context should implement the smallest versioned extension that makes the matchup explicit end to end. Do not duplicate character rules in Python and do not infer a matchup from filenames or checkpoint names.

  1. Add explicit combatant definitions to reset.

    Extend mlsim.ResetRequest with a seat-to-definition mapping (or two validated descriptors). Use those IDs in StartBattlePayload.Seats. Record them in replays and episode metrics. Preserve an explicit Blade Warden legacy default only if existing Phase 2/3 tests require it; new training commands must pass definitions deliberately.

  2. Carry matchup identity through the bridge.

    Update cmd/battle-ml-sim/main.go, bridge.py, smoke/replay paths, and protocol tests. A portable replay must contain enough definition/version data to reproduce the same matchup in a fresh simulator process.

  3. Create a balanced shared-policy scheduler.

    Add both character IDs and a shared-policy mode to TrainingConfig and AuthorityGymEnv. Schedule Roles A–D evenly. Record learner character, opponent character, learner seat, opponent policy, seed, and role cell for every episode.

  4. Make inference matchup-aware.

    Extend evaluation CLI/records so Seat A character and Seat B character are separately specified. Policy artifacts remain independent from seats. Same-checkpoint and different-checkpoint runs must work in both character orientations.

  5. Audit and version the observation.

    Add explicit own/opponent combatant definition encoding. Audit non-D6 dice, dice counts above five, faces above six, target counts, card instance-to-definition features, new statuses/resources, new command types, and candidate counts above 128. If any feature meaning or dimension changes, bump the observation/action schema and retrain from scratch.

  6. Replace the Blade-only teacher.

    HeuristicPolicy and behavior-cloning demonstrations currently contain Blade Warden preferences. Implement transparent character-aware heuristics for both X and Y, or explicitly disable imitation and demonstrate a stable alternative. Balance demonstrations across Roles A–D. Never call the old heuristic a valid baseline for new characters without evidence.

  7. Keep training and evaluation separate.

    Training collects learner transitions and performs PPO updates. Evaluation loads frozen models and never constructs an optimizer. The opponent pool should include random, validated character-aware heuristics, and frozen historical shared checkpoints—not two exclusively changing learners.

  8. Update reports and compatibility metadata.

    Configs, summaries, replay records, plots, checkpoint metadata, and exports must name both content IDs, the four role cells, source/content/schema versions, and exact seed sets. Any production export needs corresponding Go encoder/runtime support and a new model ID/path; preserve the accepted Blade Warden v1 export.

Schema gate

New content can fit v1 only after measurement

Stable hash buckets make many authored IDs representable, but “it does not crash” is not proof that the model can distinguish the new decisions. Inspect actual observations and candidate features for both characters.

Potentially compatible

Existing command types, at most 128 legal candidates, familiar public/private state, five ordinary D6 dice or fewer, and abilities/cards expressible through existing candidate fields.

Still requires testsContent hash changes

Requires a schema review or bump

New command types, more dice, non-D6 semantics, new target structures, resources absent from snapshots, more than 128 candidates, or decisions whose important distinction is lost in the current hash buckets.

Retrain from scratchUpdate Go parity
Never reuse an incompatible checkpoint. If observation or action meaning changes, increment the schema version, reject old artifacts explicitly, update Python and Go encoders together when deployment is in scope, and create a new checkpoint family. Do not silently pad, truncate, or reinterpret accepted weights.

Required future runner contract

Commands must name the matchup explicitly

The flags below describe the interface the future context should implement. They are intentionally shown as a target contract: the current Phase 2 CLI does not yet accept character IDs.

Proposed explicit workflow
# Run from dice-and-destiny-server. Replace both IDs and the run slug.
CHARACTER_X_ID=character_x
CHARACTER_Y_ID=character_y
RUN_SLUG=character-x-v-character-y-shared-v1

# 1. Validate reset, privacy, deterministic replay, and candidate capacity.
./scripts/ml.sh smoke \
  --seat-a-character "$CHARACTER_X_ID" \
  --seat-b-character "$CHARACTER_Y_ID" \
  --seed 20260801

# 2. Baseline both character orientations and both seats.
./scripts/ml.sh evaluate \
  --seat-a-character "$CHARACTER_X_ID" \
  --seat-b-character "$CHARACTER_Y_ID" \
  --seat-a random --seat-b random \
  --swap-characters --swap-policies \
  --episodes 100 \
  --output "runs/$RUN_SLUG/baseline-random"

# 3. Train three shared-policy seeds across all four learner role cells.
./scripts/ml.sh train \
  --characters "$CHARACTER_X_ID" "$CHARACTER_Y_ID" \
  --shared-policy \
  --balanced-character-seat-roles \
  --seeds 41 52 63 \
  --timesteps 20000 \
  --workers 4 \
  --output "runs/$RUN_SLUG/training"

# 4. Held-out evaluation must be repeated for X and Y as the learned character,
#    in Seat A and Seat B, with model weights frozen.
./scripts/ml.sh evaluate \
  --seat-a-character "$CHARACTER_X_ID" \
  --seat-b-character "$CHARACTER_Y_ID" \
  --seat-a "model:runs/$RUN_SLUG/training/seed-41/checkpoints/final.zip" \
  --seat-b random \
  --swap-characters --swap-policies \
  --episodes 100 \
  --seed-start 12000000 \
  --output "runs/$RUN_SLUG/held-out/final-41-v-random"

# 5. Final acceptance: 1,000 games balanced across character, seat, and
#    independently trained checkpoint assignments.
./scripts/ml.sh acceptance \
  --characters "$CHARACTER_X_ID" "$CHARACTER_Y_ID" \
  --shared-model-a "runs/$RUN_SLUG/training/seed-41/checkpoints/final.zip" \
  --shared-model-b "runs/$RUN_SLUG/training/seed-52/checkpoints/final.zip" \
  --balanced-character-seat-policy-cells \
  --output "runs/$RUN_SLUG/acceptance"
Argument names may change during implementation, but the semantics may not: character identity, seat identity, policy identity, and learner identity must be independently controllable and recorded.

End-to-end runbook

From finished content to an accepted model set

  1. Protect the workspace.

    Read AGENTS.md, inspect all worktrees and current changes, create a dedicated codex/ branch/worktree from the intended reviewed baseline, and preserve every ignored checkpoint, run artifact, save, snapshot, and unrelated edit.

  2. Confirm both combatants are authority-complete.

    Each definition must load from content/battle_v1, support an external seat, enumerate every reachable planning/roll/card/ability/target/defense/reaction/status/hand-limit decision, and complete deterministic full battles without ML.

  3. Implement the matchup contract.

    Make character IDs explicit from CLI through reset, metrics, replay, configuration, and reporting. Add unit tests for X-v-Y and Y-v-X reset, viewer isolation, deterministic replay, repeated reset, and exact candidate acceptance.

  4. Freeze the representation.

    Measure maximum candidates and inspect encoded distinctions for both characters. Decide whether v1 remains valid or introduce a new version. Record the decision and add Python/Go parity tests when a runtime export is intended.

  5. Build honest baselines.

    Run large random-v-random batches in both orientations. Create and validate transparent heuristics for both characters before using them as baselines or imitation teachers. Confirm zero rejects, stale actions, wrong-seat actions, invalid indices, and unexplained truncations.

  6. Train three independent shared-policy seeds.

    Use balanced Roles A–D, disjoint reproducible seeds, terminal rewards (+1/−1/0), periodic checkpoints, random/heuristic/frozen historical opponents, and no evaluation updates. Record decisions and completed episodes per role cell.

  7. Prove learning per character.

    On held-out matched seeds, evaluate every final checkpoint as Character X and as Character Y, in both seats. Compare with random, validated heuristics, initial/untrained, behavior-cloned, and early learned checkpoints. Do not let aggregate strength on one character hide failure on the other.

  8. Run cross-play and the 1,000-game soak.

    Load two independent shared-policy instances, use same/different checkpoints, balance character/seat/policy assignments, save representative success and failure/surprising replays, and require all 1,000 games in one automated run with no process restart.

  9. Generate the evidence bundle.

    Save machine-readable configs, packages, hashes, seeds, checkpoints, curves, role-cell results, cross-play matrix, distributions, action frequencies, throughput, latency, replays, and a human completion report with explicit pass/fail criteria.

  10. Export only after acceptance.

    If the model will be used in Godot, create a new named export and update the Go/runtime compatibility contract. Keep the accepted Blade Warden artifact untouched. Run proxy-human and graphical acceptance separately for the new matchup.

Mandatory acceptance gates

The new model set is not accepted unless every category passes

CategoryRequired evidence
A · Content and authorityX-v-Y and Y-v-X start and finish through the real authority; all inputs are enumerated; private information remains viewer-safe; existing PvE and accepted Phase 1–3 behavior remains available.
B · Shared-policy identityOne checkpoint controls Character X and Character Y. Roles A–D are trained and evaluated. Character, seat, policy, and learner assignments are explicit and independently swappable.
C · Repeated episodesAt least 1,000 consecutive final-model battles in one automated process, balanced across character/seat/checkpoint cells, with unique IDs/seeds, complete results, and zero crashes, rejects, stale, wrong-seat, invalid, state leaks, or unexplained truncations.
D · Actual learningThree training seeds; real-authority experience consumed by optimizer updates; changed parameters; initial/intermediate/final checkpoints; disjoint held-out seeds; final beats random with the 95% lower confidence bound above 50% separately when controlling X and when controlling Y.
E · Comparative evidenceFinal beats initial/early checkpoints for both characters; heuristic performance is measured separately; same-checkpoint and different-checkpoint cross-play works; no nominal mirror result is presented as learning proof.
F · Bias analysisReport win/draw/truncation rates and confidence intervals by character, seat, opponent, and checkpoint. State whether character balance, initiative, or reaction priority creates measurable advantage.
G · ReproducibilitySource/content/schema/model versions, exact character IDs, configs, seed rules, role schedule, opponent pool, reward, packages, hardware, checkpoints, and evaluation seeds are saved. A same-seed probe substantially reproduces behavior.
H · ArtifactsCurves, checkpoint win rates, per-character baselines, cross-play matrix/rating, role-cell table, duration/health distributions, action frequencies, invalid counts, games/s, latency, success and failure/surprising replays, checkpoints, JSON config/index, and human report.
I · Runtime safetyAny exported model uses a new ID/path, validates all hashes and schema dimensions, matches Python inference, and cannot mutate authority state directly. Accepted older artifacts remain reproducible and unchanged.
J · RegressionAll relevant Go tests, go vet, race tests, ML tests/lint/lock, Phase 2 smoke/replay, Phase 3 inference parity/proxy tests if touched, and Godot authority verification pass.
Failure rule: if either character fails a mandatory learning gate, the shared model set is incomplete even if the aggregate result looks strong. Continue diagnosing representation, character-aware teaching, role balance, training budget, reward design, or authority/content defects. Report the failure honestly.

Stop conditions

Do not spend compute on an invalid experiment

  • Either character cannot complete full external-controller battles.
  • A viewer sees opponent private hand, planning, dice, or future random state.
  • Any legal decision is missing from authority candidates.
  • Candidate capacity exceeds 128 without a reviewed schema change.
  • The encoder cannot distinguish strategically different new actions.
  • The only available heuristic is the unvalidated Blade Warden heuristic.
  • Role scheduling is not balanced or cannot be audited from artifacts.
  • Evaluation seeds overlap the generated training seed space.
  • Any model command bypasses or is rejected by the authority.
  • An accepted model/export would be overwritten or made unreproducible.
