Core improvement 1

Champion-gated, reversible, history-driven training

Use two distinct champion concepts

Checkpoint champion

The strongest accepted checkpoint within the current campaign/model family. Every new challenger must beat this model first.

Global champion

The strongest accepted model across all campaigns and model families. Currently raw checkpoint 480; checkpoint 400 is retained as the prior champion. It changes only after the global promotion series passes.

Adaptive checkpoint gate

Use deterministic policies, real authority, fresh held-out seeds, and seat swaps. Define draw-adjusted score as:

adjusted_score = (challenger_wins + 0.5 * draws) / games
First block

1,000 games = 500 fresh seeds, each played twice with seats swapped.

→
Decide or expand

≥52% passes. ≤48% fails. Strictly between 48% and 52% triggers another fresh block.

→
Gray-zone block

3,000 games = 1,500 new seeds with swaps. >50% passes; ≤50% fails. Preserve the combined 4,000-game report too.

A passed challenger replaces the checkpoint champion. A failed challenger is not continued: restore the immutable checkpoint champion and its optimizer state, then create a controlled child experiment.

Global promotion gate

  • If checkpoint champion and global champion are the same model, the first checkpoint gate can serve as global block one, but promotion confirmation is still required.
  • If they differ, begin a new held-out global series after the checkpoint gate passes.
  • Each global block is 1,000 games using a distinct 500-seed seat-swapped list.
  • If the challenger does not beat the global champion in block one, stop the promotion attempt. The global champion holds.
  • If the challenger wins block one, run block two. If the series becomes 1–1, run block three.
  • Promote only if the challenger wins at least two blocks, has pooled adjusted score above 50%, the declared confidence/non-inferiority rule passes, and all safety counts are zero.
  • A checkpoint that completes this gate becomes global champion immediately. Do not wait for a later training checkpoint.

Continue on upward global progress

Below 50% does not mean stop. A sequence such as 25% → 32% → 35% against the global champion is meaningful progress. Continue the campaign while checkpoint champions improve toward the global champion.

Use a stable development anchor seed bank for comparable trend measurement and separate sealed/fresh promotion seeds. Do not use evaluation games as PPO training experience. Restart review is triggered by plateau/regression, not merely failure to cross 50%.

Default failure and plateau policy

  • Three controlled challenger failures from the same checkpoint champion: declare that recipe branch plateaued and review a new-campaign control.
  • Checkpoint champions continue improving internally and their global scores rise: continue, regardless of being below 50%.
  • Several checkpoint champions show no meaningful global-score improvement: diagnose a global-objective plateau. Use confidence intervals and a configurable minimum effect rather than point estimates alone.
  • Global scores regress: preserve the best checkpoint/global models, roll back, and change the suspected control.
  • Promotion resets checkpoint-failure patience. Global promotion resets global-stagnation tracking.

Opponent population: champions only

Replace directory-driven “all saved checkpoints” sampling with an explicit immutable champion registry. PPO opponents may be:

  • Current frozen checkpoint champion
  • Current frozen global champion
  • A small hall of prior checkpoint/global champions retained because they were once promoted and represent distinct successful strategies

Do not add ordinary checkpoints merely because they were saved. Deduplicate identical champion paths and apply explicit category weights so file count cannot change sampling probability. Teacher/random policies may be separate opt-in ablations or initial curriculum diagnostics, but are not part of the main three-hour PPO opponent pool.

Core improvement 2

Create a scalable, explicit, status-aware Observation V3

Observation V2 allocates 18,944 float32 values: 2,560 base values plus 128 candidates × 128 values. It improved ability mechanics, but important state is absent and several capacities do not scale.

Confirmed V2 deficiencies

AreaCurrent behaviorRequired V3 behavior
StatusesOnly each actor’s status-instance count. Identity, stacks, polarity, lifecycle, and trigger are discarded.Encode every viewer-visible active status as an entity with owner, identity/mechanics, stacks, limits, polarity, trigger/lifecycle, effects, and current relevance.
HealthCurrent/max ratio plus max/30; no explicit normalized current points.Encode current/scale, max/scale, and current/max. Derive scale from frozen content manifest rather than unexplained fixed 30.
SymbolsEight slots across the entire content catalog. Nine catalog symbols hard-fail; sorted insertion can shift semantics.Build a stable campaign vocabulary/embedding manifest from the eligible roster and referenced content. No fixed global eight-symbol ceiling.
AbilitiesAt most 12 active offensive+defensive abilities, 6 tiers, 2 requirements/tier. Only own active board.Shared variable/entity encoding sized from maximum simultaneously active board, including explicit passive/form state and prospective transformation mechanics.
FormsNo explicit form concept.Encode current form and active board. For a human/werewolf with 16 abilities per exclusive form, size for 16 simultaneous abilities—not 32—unless both boards remain concurrently relevant.
CardsBase sees counts; legal candidates get generic summaries. Identity and nuanced mechanics can alias.Encode viewer-visible hand entities up to manifest-derived maximum hand size. Do not allocate one slot for all 1,500 catalog cards; encode only state-relevant entities and candidates.
Opponent stateMostly scalar counts; revealed opponent dice/planning/board details are not explicitly encoded.Encode only information actually visible in the viewer-safe snapshot, including revealed opponent dice/planning when present. Never expose private hand, card instances, or hidden rolls.
Dice layoutDeclares 10 dice, but the tenth die feature range overlaps the first ability range. Current five-die content avoids it.Generate non-overlapping offsets from the schema manifest and test every maximum-capacity boundary.
ActionsHard maximum 128. Fixed 10 command types and seven broad operation-summary dimensions.Preflight worst legal-candidate bounds, version command/effect vocabulary, fail on unsupported mechanics, and use sparse shared candidate scoring so padded capacity does not dominate compute.

Frozen campaign content manifest

Before model construction, scan the entire eligible training universe—not merely the current matchup—and write a hashed manifest that determines:

  • Eligible combatants and forms
  • Stable symbol vocabulary
  • Maximum simultaneously active dice, abilities, passive entities, statuses, tokens, and visible hand cards
  • Maximum tiers and requirements or a variable nested encoding
  • Supported operation and command vocabulary
  • Maximum authority legal-candidate count, backed by generated/adversarial scenario coverage
  • Health, energy, stack, hand, target, and other normalization scales

Freeze the manifest for training, evaluation, export, and deployment. New incompatible content creates a new schema/model-family version. Do not silently resize an existing model.

Dynamic without waste

Stable Baselines uses a fixed observation/action shape for one model, but computation need not process every padded slot. Use masked shared encoders and pooling/attention over only valid entities. The public shape may reserve the manifest-derived maximum while the sparse path computes only occupied rows. A catalog with 1,500 cards must not create 1,500 per-state card slots if the viewer can hold only a small hand.

Recommended V3 architecture contract

  • Scalar context: round, segment, priority, explicit health/energy/card-zone counts, roll budget, form, defeat state.
  • Dice entities: owner/visibility, face/value, kept state, symbol embeddings/counts.
  • Ability entities: active form/board, offensive/defensive/passive role, cost/usage/targeting, tier requirements/progress, effect summaries, selected/qualified state.
  • Status entities: owner, stable ID embedding or complete mechanics signature, stacks/limit, polarity, activation timing/mode, lifecycle, operations/triggers.
  • Card entities: only viewer-visible relevant cards, identity/mechanics, energy cost, operations, zone; opponent private identities remain absent.
  • Candidate entities: original legal command type/payload references plus mechanics-derived linked entities. Preserve candidate order and exact command submission.
  • Actor: scores valid candidates with shared weights conditioned on pooled context/entities.
  • Critic: sees a stable pooled state representation and records calibration telemetry. Keep dense/base/pooled critic choices versioned.

Avoid hand-authored rules such as “Golden Edge equals 6.” It is acceptable to use stable learned ID embeddings tied to the frozen manifest, but mechanics must be explicit enough that new content is not forced into false equivalence.

V3 safety and parity gates

  • Python and Go encoders match within the declared float contract on fixed and generated corpora.
  • Viewer-private mutation tests prove opponent hand/card instances/hidden rolls do not affect observations.
  • Status identity/stack mutations do affect the intended status entity and no unrelated features.
  • Exclusive form changes replace active ability entities without summing inactive boards; persistent cross-form state remains encoded.
  • Maximum manifest capacities do not overlap or truncate. Overflow fails loudly before training.
  • All legal candidates, masks, deterministic actions, submitted commands, terminal results, and replays retain authority parity.
  • V2 checkpoints remain loadable as opponents. Never reinterpret V2 weights as V3.
  • Exports include schema/manifest/content/source/checkpoint hashes and Go inference parity.
Core improvement 3

Remove automatic post-PPO teacher rewriting

Default rule: the main campaign ends with its raw PPO checkpoint. Do not run the prior 600-state × 60-epoch corrective clone, do not overwrite the raw model, and do not select a model because it agrees with the teacher.

Why

  • The mechanics teacher uses a transparent, local, one-roll utility heuristic—not terminal win probability.
  • It ignores important context such as health, overkill, opponent response, long-term resources, and active status strategy.
  • The V3 correction repeatedly trained 600 teacher-labelled first-roll states for 60 epochs at LR 1e-4 without games or terminal rewards.
  • Teacher agreement rose, while complete-game strength fell from raw checkpoint performance to corrected V3’s 60.2% raw wins against V2.
  • Corrected V3 lost directly to every sampled raw checkpoint.

Permitted teacher use

  • Initial warm start: optional and separately configured. It may move a random network toward legal, live mechanics before PPO. Stress-test teacher warm start versus no/alternative warm starts using complete games, not only imitation accuracy.
  • PPO opponent: excluded from the main owner-selected champion-only population. It may be an explicit ablation outside the main campaign.
  • Post-PPO correction: off by default. If explicitly tested later, clone the raw checkpoint into a separate artifact, preserve both hashes, and run corrected clone versus raw parent through the same checkpoint gate. Failure rejects the clone; success only earns the normal global gate.
  • Teacher agreement: diagnostic only. Never an acceptance criterion.

For this three-hour campaign, use no post-PPO correction. The final tested challenger must be the raw outcome-trained checkpoint.

Controlled response to a failed challenger

  1. Reject the challenger and restore checkpoint champion weights plus optimizer.
  2. Use telemetry to pick one resume-safe change. Record hypothesis before training.
  3. Prefer conservative first responses: lower LR when KL/clipping/weight movement is high; fewer epochs or target KL when updates are too large; entropy adjustment only when exploration evidence supports it; critic controls when explained variance/calibration is poor; pool weights when opponent/forgetting evidence supports it.
  4. Do not use the failed evaluation games for PPO.
  5. After three controlled failures from the same parent, declare that branch plateaued. If campaign time remains, start only a predeclared new-campaign alternative whose initialization cost is justified; otherwise stop with preserved evidence.

At stop, run a final comparison of the best V3 checkpoint against the current registered global champion if the exact required promotion evidence has not already been completed. This final evaluation is allowed as part of finishing the campaign outcome.

If a new global champion emerges

  • Immediately preserve raw checkpoint, optimizer state, config, manifest, ledger, seed lists, evaluation records, and hashes.
  • Update the global champion registry atomically; do not delete the previous champion.
  • Export the new V3-family actor under a new model ID/file. Do not overwrite accepted V1, V2, or the existing corrected V3 export.
  • Run Python/export/Go inference parity, complete authority replay, native tests, and relevant Godot learned-battle smoke before calling it deployable.
  • Report exact W/D/L/draw-adjusted scores for every global block and the pooled result.

If no new global champion emerges

  • This is not a failed engineering task if all three systems work correctly.
  • Preserve the strongest V3 checkpoint, its score against the current global champion, its checkpoint progression, and why the campaign stopped.
  • State whether global score improved over time, plateaued, or regressed.
  • Use the ledger to recommend the next single controlled campaign change.
