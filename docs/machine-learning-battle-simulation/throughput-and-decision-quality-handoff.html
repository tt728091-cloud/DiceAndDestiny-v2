Zero-context implementation + experiment guide

Make battles fast first. Then make decisions better.

This page gives a fresh Codex context the complete two-phase contract: optimize the real-authority training path from the measured 1.8474 complete games per second toward 20–30 games per second on the M3 Max, prove exact behavior parity after every optimization, obtain owner acceptance, and only then improve dice/ability learning without hardcoding a preferred attack.

Executive contract

Two owner-reviewed projects, not one uncontrolled rewrite

A future context may read both phases, but it must implement only the phase explicitly authorized. Phase 1 stops for review with benchmarks and parity evidence. Phase 2 starts from the accepted Phase 1 result in a separate task/branch and never becomes an excuse to change battle rules or balance.

NON-NEGOTIABLE 01

The real authority remains the game

No approximate Python rules, skipped reactions, fabricated candidates, hidden-state access, shortened battles, or simplified “training-only” combat logic. Speed comes from removing redundant infrastructure work and adding safe concurrency.

NON-NEGOTIABLE 02

Measure after every material change

Do not stack ten optimizations and benchmark only at the end. Each step records before/after speed, CPU, memory, allocations, failures, and correctness parity so regressions and false wins remain attributable.

NON-NEGOTIABLE 03

Information is not strategy steering

Phase 2 may expose authored mechanics, remaining rolls, tier requirements, and outcomes. It may not hardcode Sword Cut preferences, human tactical rules, or damage-shaped rewards and then call the result discovery.

NON-NEGOTIABLE 04

Maximum first, controllable headroom second

Phase 1 must discover the fastest safe sustained configuration, then turn its resource measurements into lower-impact launch profiles so the owner can reserve part of the computer while training.

Mandatory phase gate: Phase 2 does not begin merely because Phase 1 code exists. Phase 1 requires an owner-reviewed performance report, exact parity evidence, stable benchmark commands, complete verification, and an explicitly accepted baseline.

Optimization ladder

  1. Freeze the baseline and add profiling.

    Create stable fixed-seed benchmark commands and machine-readable output before behavior changes. Add Go full-battle benchmarks and local CPU/allocation profiles; profile Python orchestration/JSON/encoding separately. Record source/content/schema/checkpoint hashes, hardware, power mode, replay mode, worker count, Torch threads, and duration.

  2. Cache immutable content and participant templates.

    Load/validate the settled BattleLibrary once per content hash or simulator process. Avoid repeated disk loads, full-library marshals/unmarshals, and immutable catalog copies on reset/step. Preserve the pinned serialized catalog/hash for replay and compatibility. Cache objects must be immutable and safe across concurrent battles.

  3. Remove avoidable legal-action and observation work.

    Precompute canonical JSON sort keys once per candidate instead of marshaling within every comparison. Reuse the post-command state/result to identify and encode the next decision rather than issuing redundant repository-backed OpenBattle calls. Preserve candidate completeness, exact stable order, viewer filtering, and command identity.

  4. Add explicit lightweight telemetry modes.

    Routine training needs compact per-step fields, terminal metrics for every game, and representative replays—not a full replay payload crossing the bridge every episode. Add none/compact/representative/full modes, asynchronous or buffered artifact writing where safe, and compressed archives for large retained traces. Acceptance/debug modes remain exact and available.

  5. Build a parity-proven ephemeral training authority.

    Own one battle directly in memory and continue to call the exact engine, RNG, legal-action generation, viewer filtering, and original-command application. Avoid repository load/save clones, full accumulated-event validation, and copying immutable content on every action. Retain compact incremental trace data. Compare command-for-command against the normal authority across a broad fixed corpus before using it for training.

  6. Compact the Go/Python boundary.

    Measure first, then reduce large JSON object traffic. Options include a minimal transition schema, Go-side observation/action encoding with exact Python parity, binary float/mask frames, batched requests, shared memory, or an in-process native binding. Never let transport optimizations change viewer safety, float schema, masks, candidate order, or the submitted original command.

  7. Add true CPU-parallel rollout collection.

    Replace sequential DummyVecEnv stepping with measured multiprocessing or a Go-native concurrent battle pool. Each battle owns isolated state and deterministic seeds. Batch policy inference, prevent Torch/BLAS oversubscription, and sweep worker counts rather than assuming 16 is best. Start with 8–12 as a hypothesis, not a setting.

  8. Add a user-selectable resource budget.

    After finding the maximum sustained configuration, expose a documented training-launch setting such as max, balanced-80, light-50, and an explicit custom worker/thread budget. Implement the budget with worker limits, Torch/BLAS thread caps, bounded inference and I/O concurrency, and platform-supported process priority or CPU placement where useful. Do not use hidden sleeps or discard experience to manufacture a lower number. The setting must be recorded in checkpoints, run metadata, and reports.

  9. Parallelize independent experiment work.

    Run independent seeds and evaluation shards concurrently when memory/CPU allow. This reduces wall time even when one PPO seed remains centrally learned. Keep artifacts, seed ranges, processes, and output roots isolated. Distributed multi-computer rollout is future-capable but not required for this single-computer phase.

  10. Consolidate only after attribution is clear.

    Once individual wins are measured, choose the smallest safe combined architecture. Rerun the complete saturation sweep, long soak, parity corpus, profiling, artifact-size comparison, and all regressions. Remove abandoned experimental paths rather than leaving multiple unmaintained simulators.

Likely high-value hotspots visible today: repeated settled-catalog JSON decoding; battle/checkpoint/event-history cloning and validation; redundant viewer results/legal-action generation; JSON serialization across the pipe; terminal replay transfer; and the absence of simultaneous simulator execution. Profiling decides their actual order.

Phase 1 experiment discipline

Every optimization is a falsifiable experiment

  1. State one hypothesis.

    Example: “Repeated settled-library decoding consumes at least 20% of single-lane CPU time.” Name the profile evidence and expected effect before editing.

  2. Make the smallest coherent change.

    Do not mix content caching, protocol replacement, and multiprocessing in one result. Preserve unrelated user changes and current ignored artifacts.

  3. Run focused correctness tests first.

    Reject any implementation that changes legal candidates, viewer visibility, action acceptance, deterministic trace, or terminal result before spending time on throughput.

  4. Run identical before/after benchmarks.

    Use the same seeds, checkpoint, replay mode, worker count, power conditions, and sample length. Repeat enough times to report median and variability rather than one favorable run.

  5. Keep or revert by evidence.

    Retain the change only if it produces a material sustained win without correctness, maintainability, memory, or artifact regressions. Record unsuccessful experiments too; they prevent repeated dead ends.

  6. Update the bottleneck.

    Profile again after each major win. The limiter will move from authority work toward process coordination, inference batching, optimizer work, memory bandwidth, or artifact I/O.

Maximum mode and owner-headroom modes

The optimization target remains the fastest safe sustained complete-game throughput. Lower percentages are operational controls derived from that result, not substitutes for finding it. A requested percentage is a resource ceiling/profile selection; it does not promise the same percentage of maximum games/s because scaling is not linear.

RequirementPhase 1 contract
Maximum profileUse the worker, inference, thread, buffering, and I/O configuration that produces the highest stable 30–60 minute games/s without swap growth, thermal collapse, or correctness failures. This is the primary result and the basis for the 20–30 games/s objective.
Approximately 80% profileChoose a measured configuration intended to consume no more than about 80% of total CPU capacity under the named power mode while preserving useful memory and interactive headroom. Validate actual sustained usage and responsiveness; do not merely multiply maximum workers by 0.8 and assume success.
Light/custom profilesProvide at least one approximately 50% profile plus explicit worker and Torch/BLAS-thread overrides. Reject impossible or unsafe combinations with a clear error. Preserve deterministic seed ownership and artifact isolation at every setting.
Launch interfaceExpose the profile through the normal documented training command/configuration, with maximum as an explicit choice rather than an invisible default. Print the resolved worker/thread/memory-sensitive settings before training begins.
CalibrationStore machine identifier, core topology, power mode, software/content hashes, normalized CPU, memory pressure, swap, thermal/performance warnings, throughput, and responsiveness for each profile. Warn when the machine or architecture has changed enough that the saved calibration should be rerun.
Meaning of “80%”Define CPU as a normalized percentage of the machine's total schedulable capacity so Activity Monitor-style multi-core totals are not confused with one-core percentages. Treat the cap as best-effort on macOS: verify observed sustained use and prefer leaving real measured headroom over claiming false precision.
Responsiveness matters separately from average CPU. Include a small repeatable foreground probe—such as command latency or a lightweight interactive workload—during calibration. If an “80%” run still makes normal desktop work unpleasant because of memory pressure, priority, thermals, or bursty saturation, lower its concurrency until it satisfies the headroom goal.

Phase 2 · decision quality

Give learning the mechanics, not a prescribed move

This phase starts only after Phase 1 acceptance. Its purpose is to eliminate a systematic “take any qualified ability immediately” bias and let the policy compare rolling, rerolling, keeping, cards, targets, and qualified attacks using structured authority-owned mechanics.

Observed failure case: in battle learned-1785691059-2718787-15088, seed 1785691061228807, the model rolled [6,1,3,4,2], had three swords and two rolls remaining, received 68 legal candidates, and immediately chose Sword Cut for five damage. Rerolling only indices [0,3] preserved the three swords and could reach six or seven damage. Ignoring reactions, the two remaining rolls yield about 6.5 expected Sword Cut base damage.

Phase 2 implementation sequence

  1. Freeze tactical diagnostic states.

    Reconstruct the exact owner-reported seed/decision plus a generated held-out suite covering partial tiers, competing abilities, straights/sets/symbol counts, cards, statuses, different remaining rolls, and cases where committing immediately really is best. Record all legal candidates and current checkpoint scores/probabilities. Do not label every state with a hand-authored move.

  2. Design a viewer-safe mechanics schema v2.

    Represent explicit rolls used/max/remaining, die identity/faces/symbols, kept/rerollable state, the viewer's authored ability board, each tier's normalized requirements and progress, qualified/current tier, target/effect summaries, resource costs, damage/prevention/status/resource operations, and candidate links to those mechanics. Use versioned bounded/variable structures without lossy tiny ID buckets as the primary meaning.

  3. Prove information and privacy coverage.

    For every reachable decision, show that strategically distinct options produce distinguishable encodings while opponent hands, hidden planning, private dice, unrevealed commitments, and future RNG remain absent. Audit candidate and observation capacities for future characters rather than preserving five-D6 assumptions accidentally.

  4. Replace the biased teacher or narrow its role.

    Do not hardcode ability names or “always reroll for more damage.” Prefer generic shallow authority lookahead/search that evaluates legal roll/keep/reroll/card/commit continuations from real rules, or use imitation only for liveness/syntax and allow PPO/population play to learn strategy. Any search expert must use viewer-safe state and authoritative clones.

  5. Keep the true objective honest.

    Terminal win/loss/draw remains the primary RL objective. Do not add raw damage reward shaping merely to fix this example. If potential-based or auxiliary learning is explored, isolate it in an ablation and prove it improves held-out win probability without farming damage, prolonging games, or neglecting defense/status strategy.

  6. Run the ablation matrix.

    Compare current schema/teacher, more training with the current recipe, v2 with current teacher, v2 with mechanics-aware search teacher, v2 with reduced/no strategic imitation, and at least two budgets such as 20k and 200k steps. Use three seeds, matched held-out evaluation, and the same opponent pool. Increase budget only while curves/evaluation justify it.

  7. Train with population diversity.

    Mix random, validated generic heuristics/search, current learner, accepted frozen checkpoint, and historical v2 checkpoints. Do not rely exclusively on two changing learners. Preserve separate training and evaluation paths and exact character/seat/policy metadata.

  8. Evaluate decisions and games.

    Report win rate against random, the old heuristic, the accepted v1 checkpoint, earlier v2 checkpoints, and held-out search/value estimates. Analyze rolls used, reroll subset quality, ability tier at commitment, qualified attacks declined, cards/reactions, loops, truncations, and value left on the table—conditioned on state rather than enforcing “always reroll.”

  9. Export only after complete acceptance.

    A schema-v2 checkpoint requires a new model ID/path and exact Python/Go encoder/inference parity. Never overwrite or reinterpret the accepted Blade Warden v1 checkpoint/export. Run the graphical learned-opponent acceptance separately.

What “not steering” means here: the policy receives the same structured mechanics a competent player can inspect, and a generic search/teacher evaluates all authority-legal continuations. No code says “if three swords, pursue Sword Cut,” and no acceptance rule requires one fixed move when another choice has comparable win value.
