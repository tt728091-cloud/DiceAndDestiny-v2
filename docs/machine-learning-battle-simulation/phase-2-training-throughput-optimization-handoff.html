Executive verdict

The 1.98 games/s result is not a fundamental ceiling

The new bottleneck is the whole synchronous v2 PPO pipeline, not the Go battle rules alone and not one isolated function. In the selected 200k-step seed-22 run, collection and PPO optimization consumed almost equal wall time. The strongest near-term opportunities are inside process/thread configuration, opponent lifecycle, and the neural policy's treatment of padded candidate slots.

Recommended mission: target at least a reproducible 2× improvement in learner steps/second on the unchanged v2 PPO recipe, with 3× as a stretch. A lower safe plateau is acceptable only if profiling proves the remaining limits. Measure complete games/s too, but use learner steps/s as the primary throughput measure because model behavior changes episode length.

Highest-confidence sequence

  1. Freeze a reproducible, instrumented v2 training benchmark.
  2. Correct worker thread caps and separate actor-worker threads from learner-update threads.
  3. Make opponent selection explicit and cache/reuse inference policies without changing intended probabilities.
  4. Exploit action masks so the actor scores valid candidates rather than all 128 padded slots.
  5. Only then test compact critics, torch.compile, MPS, transport redesign, shared memory, or asynchronous actor/learner systems.
Do not “optimize” by reducing PPO epochs, changing batch size, removing opponent categories, shortening battles, lowering the action cap, using approximate rules, dropping required terminal records, or weakening action/privacy checks. Those are learning-recipe or correctness changes and require separate ablations.

The main process owns MaskablePPO. Each SubprocVecEnv worker owns one AuthorityGymEnv, and each environment owns a persistent battle-ml-sim Go child. The Go process resets a fresh Blade Warden mirror authority per episode. One Gym step submits one learner action, then the Python worker drives as many opponent actions as necessary until control returns to the learner.

Selected Phase 2 configuration

  • 12 workers × 256 learner steps = 3,072 transitions per rollout cycle.
  • 202,752 total steps = 66 collection/update cycles.
  • Batch size 256 gives 12 minibatches per epoch; 8 epochs gives 96 minibatch updates per cycle, or 6,336 across the run.
  • Terminal reward only: +1 victory, −1 defeat, 0 draw.
  • Observation size: 2,560 base floats + 128 × 128 candidate floats = 18,944 float32 values.
  • Policy: mechanics-aware shared candidate scorer with width 96; maximum 128 candidate logits.
  • Opponent configuration: random, mechanics-v2, accepted v1, and historical checkpoints.
  • Authority mode ephemeral, telemetry training, transport full, learner device CPU.

Where time can accumulate

Collection side

Go reset/open/step, snapshot construction, legal actions, JSON serialization, pipe I/O, Python JSON decoding, schema v2 encoding, opponent selection/loading/inference, learner batch inference, worker IPC, rollout-buffer copies, and terminal replay/info transfer.

Update side

Eight full epochs over the 3,072-transition buffer: padded actor scoring, dense critic projection, mask application, distribution math, backward pass, gradient clipping, Adam state updates, and rollout-buffer minibatch permutation/copies.

Deep research findings

Code-level discoveries and what they imply

1 · The one-thread learner is a measured update bottleneck

set_reproducible_runtime() calls torch.set_num_threads(1) in the main process. The same main process performs all PPO updates. The v2 policy has 2,737,090 trainable parameters; 2,441,472 (89.2%) are in the current critic path, whose first layer directly projects all 18,944 observation values to 128 units.

A local batch-256 forward/backward microbenchmark using the retained seed-22 checkpoint measured approximately 58.9 ms at one thread, 37.0 ms at two, 26.1 ms at four, and 22.0 ms at eight. This is not an end-to-end promise, but it justifies a controlled learner-thread sweep before architectural changes.

First experiment: give spawned actor workers one intra-op and one inter-op thread, while separately sweeping the main learner at 1/2/4/6/8/10/12 intra-op threads. Record total CPU and contention during both collection and update phases.

2 · Training worker thread caps are probably not applied

The evaluation path explicitly sets OMP_NUM_THREADS, OPENBLAS_NUM_THREADS, MKL_NUM_THREADS, and VECLIB_MAXIMUM_THREADS, then configures PyTorch inside each evaluation worker. The training path only configures the parent. On macOS, SubprocVecEnv uses spawn; a fresh child imports PyTorch independently.

A local probe after setting the parent to one thread showed a fresh child reporting 12 intra-op and 16 inter-op threads. The current training worker does not call either PyTorch setter. This must be confirmed inside a real SubprocVecEnv worker, but it creates a credible oversubscription risk when many historical model opponents run inference concurrently.

Batch-1 policy inference also became slower at high thread counts in a local probe: v2 prediction was about 0.355 ms at one thread and 0.457 ms at twelve; v1 was about 0.297 ms at one and 0.402 ms at twelve, before multiprocess contention.

3 · Opponent models are reconstructed every episode

AuthorityGymEnv.reset() calls build_policy() for the selected opponent. ModelPolicy calls MaskablePPO.load(), which rebuilds the algorithm and policy from a ZIP. Official SB3 documentation explicitly notes that load() recreates the model from scratch. The mechanics teacher is also recreated, discarding its counterfactual outcome-table cache.

  • The retained final v2 training checkpoint is about 34.3 MB; the run's checkpoint directory is about 1.3 GB.
  • A warm local MaskablePPO.load() took roughly 57–67 ms; the first load took about 643 ms.
  • Reusing a mechanics teacher instance would retain its safe, mechanics-keyed outcome-table cache across episodes.
  • Inference opponents need actor inference state, not a full training algorithm with optimizer state.
Reproducibility caveat: ModelPolicy.reset() currently ignores episode seed and seat, while stochastic prediction uses PyTorch's process-global RNG. Repeated model construction can itself consume RNG. Establish an explicit per-episode opponent RNG contract before caching so a speed change is not silently also a strategy/randomness change.

4 · The historical “category” is not category-weighted

_available_opponents() replaces one pool: entry with every ZIP currently in the checkpoint directory, then chooses uniformly from the expanded flat list. As checkpoints accumulate, historical policies dominate the opponent probability instead of remaining one category among random, mechanics, accepted-v1, and historical.

In the selected run's 1,298 completed episodes:

  • 1,083 (83.4%) used an initial, behavior-cloned, or periodic historical checkpoint.
  • 77 used mechanics-v2, 71 random, and 67 accepted v1.

This is both a performance issue and a training-semantics issue. The next implementation must define explicit category weights, select a category first, then select a member within the historical category. If the owner wants the old expanding-file weighting, preserve it as a named legacy mode rather than assuming intent.

5 · The existing v2 encoded transport is larger and slower than full transport

The Go v2 encoder already exists and parity checks against Python. It serializes all 18,944 float32 values into base64. The raw float payload is 75,776 bytes; base64 expands it to about 101 KB before JSON framing.

A 200-decision parity probe measured mean serialized transition sizes of about 25.6 KB for full JSON versus 101.7 KB for encoded v2. Python raw schema construction averaged about 192 μs; base64 decoding/copying averaged about 261 μs. In a separate 1,000-decision serial run with identical seeds and chosen indices, full mode reached about 1,017 decisions/s and encoded mode about 935 decisions/s. Parity mode, which sends both, reached about 669 decisions/s.

Do not simply change Phase 2 to transport_mode: encoded. On the measured v2 schema it is a regression, and encoded-only transitions also cannot satisfy the current full-state mechanics teacher or cross-schema v1 model opponent without a per-policy transport design.

6 · The flat v2 observation is extremely sparse

In a 300-decision real-authority probe, the 18,944-value observation averaged 345 nonzero values—about 1.82% density. The progressing-action mask had a median of three valid actions, mean of nine, and maximum of 46 in that sample; an owner diagnostic elsewhere reached 68 raw legal candidates.

The current actor nevertheless embeds and scores all 128 candidate slots for every sample and every PPO epoch, even though masked padded scores can never be selected. A prototype that gathered nine valid candidates per sample, ran the unchanged actor layers only on those rows, and scattered logits back reduced a representative batch-256 forward/backward from about 55.1 ms to 9.6 ms at one thread while retaining the existing dense critic. A prototype combining sparse candidate scoring with a compact base critic measured about 7.5 ms.

These prototypes are directional, not accepted changes. A production implementation must prove identical valid-candidate logits/probabilities and gradient intent, cover behavior cloning and prediction paths, preserve the 128-action public contract, and run learning-quality gates.

7 · Artifact writing is not the current limiting factor

The selected run attributed about one second to artifact I/O. Checkpoint cadence and replay transport still deserve cleanup—particularly complete replay objects crossing worker IPC when only a representative is retained—but neither should outrank update compute, worker threading, opponent lifecycle, or sparse candidate scoring without new profiles.

8 · Synchronous PPO intentionally alternates collection and updates

The original PPO design alternates fresh on-policy sampling with multiple minibatch epochs. SB3 follows that model: n_steps × n_envs fills the rollout buffer, then the trainer updates. Naively collecting the next batch while updating on the previous one creates policy lag and changes the algorithm's on-policy assumptions. IMPALA and Sample Factory achieve asynchronous scaling with explicit off-policy correction; they are architectural alternatives, not drop-in PPO optimizations.

Implementation program

Do the work in falsifiable stages

  1. Stage 0 · Freeze the benchmark and add observability

    Create a unique ignored artifact tree. Re-run the exact current v2 mechanics recipe three times at 21,504 steps for iteration speed and at least once at 202,752 steps for the long reference. Record config, source diff/hash, dependency lock, content hash, machine/power state, seeds, opponent schedule, checkpoint publication order, parameter hashes, complete terminal summaries, and a representative replay.

    Add nested timings and counters for reset, opponent selection, policy construction/cache hit, opponent inference by family, learner inference, Go request operations, response bytes, Python v2 encoding, worker IPC, rollout buffer, GAE, PPO epoch/minibatch, forward, distribution/masking, backward, gradient clipping, optimizer step, checkpoint, and terminal replay serialization. Report p50/p95 and totals. Instrumentation must be switchable and low overhead.

  2. Stage 1 · Correct process resources without changing the learning recipe

    Refactor ResourceBudget to distinguish collector count, actor-worker intra/inter-op threads, and main learner intra/inter-op threads. Apply BLAS variables before spawn; initialize PyTorch inside every worker before any policy operation. Respect PyTorch's rule that inter-op threads can only be set once before inter-op work begins.

    Sweep workers 1/2/4/6/8/10/12/14/16 and learner threads 1/2/4/6/8/10/12 in a bounded matrix. Do not test every Cartesian pair blindly: profile one-worker collection, 12-worker collection, update-only replay, then select plausible pairs. Measure CPU, RSS, memory pressure, swap, thermal state, and foreground wake delay.

  3. Stage 2 · Make opponent lifecycle explicit and cheap

    Introduce a per-worker opponent manager. It should hold long-lived random and mechanics policies, a permanent accepted-v1 inference actor, and a bounded LRU of historical inference actors. Separate category weights from members. Publish historical checkpoints atomically through a manifest rather than globbing arbitrary partial/stale ZIPs.

    Create actor-only inference artifacts or load a policy state without recreating a complete PPO optimizer. Prove logits and masks match full MaskablePPO.load(). Define model-opponent stochastic RNG from episode seed, seat, policy identity, and perhaps decision index. Record those fields in episode metadata so caching cannot silently alter randomness.

    Do not combine the category-weight correction with the cache speed benchmark. First emulate the legacy expanded list exactly with caching; then test the corrected category distribution as a separate decision-quality ablation.

  4. Stage 3 · Add a mask-aware sparse actor path

    Create a versioned v2 sparse policy class rather than silently changing how old checkpoints load. Reuse the existing actor tensors and exported actor architecture. Override all relevant Maskable policy paths—forward, evaluate_actions, get_distribution/_predict, and behavior-cloning calls—so action masks are available before candidate embedding/scoring.

    Gather valid candidate rows across the batch, embed and score only those rows, scatter scores into a 128-logit tensor, fill invalid logits with the masking sentinel, and apply the official mask distribution. Handle at least one valid action per nonterminal observation and reject empty masks. Benchmark mask densities 1/3/9/32/68/128 and batch sizes used by rollout and PPO.

    Before training, prove dense and sparse valid logits, distributions, argmax, sampled actions under a fixed RNG contract, log probabilities, entropy, and actor gradients. Native runtime already iterates valid mask entries; export tensor names can remain compatible, but Python checkpoint class and hashes must still be versioned and tested.

  5. Stage 4 · Ablate a compact value network

    The deployed Go runtime exports only actor tensors, so the critic can evolve without changing runtime inference. Candidate designs include base-only value prediction; base context plus masked mean/max of candidate embeddings; or a small permutation-invariant candidate pool. Do not share value loss into actor embeddings unless that interaction is intentional and evaluated.

    This is a learning architecture change. Compare current dense critic and each compact critic at equal steps, equal seeds, equal opponent schedule, and equal wall-clock. Report explained variance, value loss, policy KL, entropy, clipping, win probability, tactical metrics, and failures. Select by time-to-quality, not update speed alone.

  6. Stage 5 · Re-profile transport and authority only after Stages 1–4

    Keep full v2 transport as baseline; existing dense base64 encoding is larger and slower. Profile whether immutable catalog construction/copying, JSON parsing, or Python schema encoding remains material after learner improvements. If so, design a sparse typed decision message containing public dynamic mechanics and only actual candidate records, or a one-time immutable catalog handshake plus compact per-step state.

    Mixed opponents need per-actor requirements: mechanics-v2 currently requires the full viewer-safe state; v1 models need v1 features; v2 models need v2 features; random needs only valid indices/types. A hybrid transport should respond according to the current actor's policy requirements without leaking hidden state. Binary framing or shared memory comes only after payload and copy profiles justify it.

  7. Stage 6 · Benchmark PyTorch compiler and Apple MPS

    Use torch.profiler to identify update operators and graph gaps. Test eager CPU against torch.compile only on stable, serializable submodules or an isolated update function. Warm up compilation outside measured windows, inspect graph breaks/recompilations, preserve uncompiled state dictionaries for checkpoint/export, and include compile latency in short-run economics.

    Test MPS rather than assuming it is faster. Measure small batch-12 rollout inference, batch-256 PPO updates, CPU↔MPS transfer, synchronization, unified-memory pressure, and unsupported/fallback operations. CPU remains the SB3 default recommendation for MLP PPO; the larger v2 update may nevertheless justify an empirical MPS lane.

  8. Stage 7 · Consider PPO recipe changes only as quality ablations

    Sweep minibatch size, epoch count, rollout length, and optional target_kl only after the engine path is fast. Each reduces or reshapes learning work. Compare equal environment steps and equal wall-clock budgets over at least three seeds. A setting is better only if it reaches or exceeds held-out decision and full-game quality sooner.

  9. Stage 8 · Sustain, report, and prepare the large campaign

    Repeat final 21,504- and 202,752-step benchmarks, then run a sustained training soak long enough to expose heat, memory growth, checkpoint-pool growth, and RNG/restart issues. Preserve every safety counter. Re-run Phase 1 throughput regressions and all Phase 2 decision/runtime gates.

    Only after owner review, start a large end-to-end model campaign using the final progress mask from the first step, explicit population weights, periodic held-out evaluations, and multiple seeds. Use staged budgets such as 2M then 10M learner decisions; continue only while learning curves justify it. Do not mix performance acceptance with declaring a new model accepted.

Benchmark protocol

Keep speed, behavior, and learning quality separate

Lane A · Deterministic engine/transport parity

Run fixed/generated corpora through full, candidate optimized, and any new transport path. Compare actor order, viewer-safe state/features, exact action mask, complete candidate order/content, original submitted command, events, RNG cursor, terminal winner/health, and retained replay. Require zero differences unless the change is an explicitly versioned learning ablation.

Lane B · Update-only performance

Capture or deterministically generate one 3,072-transition v2 rollout buffer with masks and actions, then replay PPO updates without environment time. Sweep thread/device/compiler/sparse-policy choices. Compare valid logits, losses, gradients, parameter deltas, update time, CPU, and memory. Do not call an update-only improvement an end-to-end speedup.

Lane C · Collection-only performance

Run the real learner/opponent schedule with frozen learner weights and no optimizer while retaining the same Gym step definition and terminal summaries. Measure learner steps/s and complete games/s. Include category counts and model-load/cache metrics.

Primary-source research

External references and how they constrain the plan

  1. Schulman et al., Proximal Policy Optimization Algorithms — PPO alternates sampling with multiple minibatch epochs; establishes why naive stale-rollout overlap is not a free systems change.
  2. Stable-Baselines3 2.9.0 PPO documentation — installed major/minor behavior; recommends CPU and SubprocVecEnv for MLP PPO, defines n_steps × n_envs, and documents that load() recreates a model.
  3. Stable-Baselines3 vectorized environments — process semantics, automatic reset, terminal observations, worker/core guidance, and spawn safety.
  4. SB3-Contrib Maskable PPO documentation — action masks must be implemented inside the environment for SubprocVecEnv; masking and multiprocessing are supported.
  5. Huang and Ontañón, invalid action masking in policy-gradient algorithms — theoretical/empirical basis for masking; sparse execution must preserve the masked policy distribution.
  6. PyTorch multiprocessing best practices — warns that CPU oversubscription causes contention and recommends bounding threads per process.
  7. PyTorch inter-op thread API — inter-op thread count may only be set once and before inter-op work begins.
  8. PyTorch Profiler — operator, input-shape, CPU/device activity and trace support required for update profiling.
  9. PyTorch torch.compile and compiler profiling guide — compilation modes, recompilation/guards, graph-break and trace workflow.
  10. PyTorch performance tuning guide — profiler-first optimization, operation fusion and gradient-reset guidance.
  11. PyTorch MPS API and Apple Metal acceleration for PyTorch — establishes MPS availability, not guaranteed superiority for this workload.
  12. Python 3.12 shared memory — optional later route to avoid serialization/copying, with explicit close/unlink lifecycle obligations.
  13. Go diagnostics and Go profile-guided optimization — representative CPU/allocation profiling and optional PGO only after a stable real workload exists.
  14. Apple xctrace reference — multiprocess Time Profiler/System Trace collection on the M3 Max.
  15. IMPALA and Sample Factory — asynchronous actor/learner scaling requires policy-lag/off-policy correction and belongs in a separate algorithmic phase.
