Developer Authority Transcript

Build an opt-in debug mode that explains every meaningful human, learned-opponent, D100, and automatic authority action in chronological log form—without weakening normal hidden-information rules or changing gameplay.

StatusSpecification only
Primary outputLive debug panel + JSONL

01 · Mission

Make every playtest explainable

A tester must be able to answer “what happened, who caused it, when did it happen, what changed, and was I supposed to see it?” without reconstructing the battle from screenshots or low-level commands.

Target experience: when Poison disappears because the learned opponent played Antidote, the normal public log reports the revealed play, while the developer transcript also shows the trigger batch, actual rolls, selected status, operation, stack change, authority stage, and any information that was hidden before reveal.
1 · AuthorityProduces commands, events, snapshots, automatic effects, and visibility facts.
2 · RecorderWrites immutable, ordered, structured debug records exactly once.
3 · FormatterCreates concise human-readable summaries from stable fields.
4 · Debug UIShows a live, filterable transcript without submitting gameplay commands.
5 · JSONLPreserves the complete battle for live tailing and postmortem review.

Required outcomes

  • Log every accepted human and opponent decision.
  • Log meaningful automatic authority work, not just submitted commands.
  • Explain dice, reactions, damage math, status applications/triggers/removals, resources, cards, and results.
  • Work in both classic D100 battles and learned-policy mirror battles.
  • Allow live viewing in-game and direct reading from disk.
  • Correlate every entry with battle, round, segment, stage, actor, and source IDs.

Non-goals

  • Do not change combat rules, balancing, authority ordering, or model behavior.
  • Do not expose private data in the normal player combat log.
  • Do not use transcript data as input to the learned policy.
  • Do not replace necessary player-facing presentation fixes with “read the debug log.”
  • Do not add cloud logging, accounts, networking, or production telemetry.
  • Do not rewrite developer history/snapshots; integrate cleanly with them.

02 · Current state and gap

Build on what exists, but do not mistake it for the transcript

Learned diagnostics

phase3/learned-battles.jsonl currently records battle metadata and accepted human/model decision commands. It proved that Antidote targeted Poison, but it did not record the Poison die faces or every automatic outcome.

Viewer-safe result

The normal authority result intentionally filters snapshots and events for one viewer. Preserve that boundary. It is the correct source for the player UI, but it cannot provide an omniscient developer postmortem by itself.

History and inspector

Developer history supports rewind/replay in standard battles, and the inspector exposes current UI state. Neither is a complete, plain-language, learned-battle authority audit trail.

Do not reconstruct truth from the rendered UI. Record authoritative facts at the common Go authority/engine boundary before viewer filtering, then expose them through a separate debug-only channel.

03 · Visibility contract

Show developers everything, and label why players cannot

Every record must carry an explicit visibility classification at the moment represented by that record. The transcript may be omniscient only because it is debug-only. The ordinary combat log continues to receive only viewer-safe public facts.

ClassificationMeaningExamplesNormal player log
PUBLICLegitimately revealed to both combatants now.Revealed ability, played Antidote, final defense reveal, committed damage, applied/removed status.May be displayed.
PRIVATE_SELFKnown only to the human viewer until a later reveal.Human hand, secret defense selection, unresolved private die result.Only in the owning player’s private UI where rules allow.
PRIVATE_OPPONENTKnown only to the opponent/authority until reveal.Opponent hand, secret reaction choice, secret defense selection or die.Never before reveal.
DEBUG_SYSTEMDeveloper mechanics rather than game-world knowledge.Candidate index, model latency, checkpoint IDs, pending-input ID, source correlation, authority rejection.Never.
Security gate: omniscient records must never travel through the ordinary viewer-safe result or normal combat-log fields. Enable the recorder and panel only when OS.is_debug_build(), an explicit environment opt-in, and the matching project development setting all permit it. Default to off. Release builds must not be able to enable it accidentally.

Reveal transitions are separate facts

A private fact does not become retroactively public. Record the private choice when it occurs, then record a later public reveal referencing the original record/source. This makes secret simultaneous flows auditable.

[PRIVATE_OPPONENT] Learned Blade Warden selected Basic Defense
[PRIVATE_SELF]     Human selected Basic Defense
[PRIVATE_OPPONENT] Learned Blade Warden rolled defense face 4
[PRIVATE_SELF]     Human rolled defense face 3
[PUBLIC]           Defenses revealed: Learned Basic Defense 4; Human Basic Defense 3

04 · Canonical records

Structured first, readable second

JSONL is the canonical artifact. The in-game transcript and terminal formatter must render from the same structured records so wording can improve without losing facts.

Required envelope

  • schema_version and recorder version
  • recorded_at_utc, monotonic sequence, and optional caused_by_sequence
  • battle_id, seed, mode, human/model seats, controller
  • round, segment, stage, window and pending-input correlation IDs
  • kind, actor/target IDs, source/proposal/status/card/ability IDs
  • visibility and optional reveal/reference sequence
  • A concise summary plus typed details

Record families

  • Battle lifecycle and segment/stage transitions
  • Decision offered, command submitted, accepted, or rejected
  • Ability/card/status selection and reveal
  • Die requested, rolled, modified, and revealed
  • Status applied, stacked, triggered, outcome evaluated, decremented, or removed
  • Damage proposed, defended, prevented, modified, converted to card loss, and committed
  • Energy/card-zone/health/resource changes
  • Model inference metadata and final battle result

Illustrative JSONL record

{
  "schema_version": 1,
  "recorder_version": "authority-transcript-v1",
  "recorded_at_utc": "2026-08-02T14:22:31.125Z",
  "sequence": 87,
  "caused_by_sequence": 86,
  "battle_id": "learned-example",
  "round": 2,
  "segment": "ongoing_effects",
  "stage": "status_roll_reaction",
  "kind": "status_removed",
  "actor_id": "seat-b",
  "controller": "learned_policy",
  "visibility": "public",
  "summary": "Learned Blade Warden's Antidote removed Poison ×2",
  "details": {
    "card_definition_id": "antidote",
    "status_id": "poison",
    "stacks_before": 2,
    "stacks_removed": 2,
    "stacks_after": 0,
    "operation": "remove_status"
  }
}
A command is not an outcome. “Opponent submitted card instance 007 with choice poison” is useful system evidence, but the transcript must also resolve the instance to Antidote and record the resulting Poison stack mutation. Record actual die faces; do not leave [?, ?] once the authority knows them.

Required Poison narrative

ROUND 1 · DAMAGE RESOLUTION
[PUBLIC] Human's Venom Strike dealt 3 damage to Learned Blade Warden
[PUBLIC] Venom Strike applied Poison ×2 to Learned Blade Warden (0 → 2)

ROUND 2 · ONGOING EFFECTS
[DEBUG_SYSTEM] Poison ×2 opened two status rolls for Learned Blade Warden
[PRIVATE_OPPONENT] Poison dice rolled: [2, 6]
[PUBLIC] Poison dice revealed: [2, 6]
[PUBLIC] Learned Blade Warden played Antidote targeting Poison
[PUBLIC] Antidote removed Poison ×2 (2 → 0)
[DEBUG_SYSTEM] Face 2 proposed 1 Poison damage; face 6's one-stack recovery was redundant after Antidote
[PUBLIC] Poison damage resolved: 1

The exact ordering must come from authority behavior and tests; the example demonstrates the required explanatory depth, not permission to hardcode Poison-specific logic.

05 · Developer interface

Readable during play and useful afterward

In-game panel

  • A visible DEV TRANSCRIPT toggle in debug mode only.
  • Chronological, scrollable entries grouped by round and segment.
  • Color/badge visibility labels and actor names, not only instance IDs.
  • Filters: All, Public, Human, Opponent, Hidden, System, Errors.
  • Follow-latest toggle, pause scrolling, search, copy visible, and copy/export battle.
  • Show current battle ID and output path.
  • Opening, closing, scrolling, and filtering must never send a gameplay command or pause authority progression.

Disk and terminal

Use workspace-isolated paths through WorkspacePaths. A stable append-only live file is easiest to tail:

dice-and-destiny-client/.godot/runtime/workspace/client/user/debug/authority-transcript.jsonl

Recommended live command:

tail -F dice-and-destiny-client/.godot/runtime/workspace/client/user/debug/authority-transcript.jsonl

Optionally add a small formatter script that prints summary with round/segment/visibility. Keep the raw JSONL authoritative.

Normal combat log versus developer transcript: improve the normal combat log whenever an action is legitimately public—such as “Opponent played Antidote; removed Poison ×2.” The developer transcript additionally exposes hidden and system facts with labels. Do not make the debug panel the only place public gameplay feedback exists.

Required design properties

Exactly once

One authoritative fact produces one record. Use monotonic sequence numbers and correlation IDs; UI rerenders must not duplicate records.

Generic

Format from typed operations and content catalog names. New characters, cards, statuses, and dice should appear without bespoke logging code.

Non-invasive

Recorder state cannot affect RNG, candidate ordering, authority validation, model observation, snapshots, or battle results.

Failure-aware

Log rejected/stale/wrong-seat commands and inference errors. A log write failure must surface clearly in debug mode without fabricating gameplay.

Bounded

Stream to disk and virtualize or cap rendered UI rows. Do not retain an unlimited duplicate transcript in the render loop.

Versioned

Version schema and formatter. Unknown fields are tolerated; incompatible schema changes fail explicitly in tests/tools.

Do not log by scraping labels. UI text such as “Final 0,” “Pending 3,” or a hidden card placeholder is presentation, not authority truth. Derive records from commands, typed operations, events, and before/after authoritative state.

07 · Startup and gating

One explicit debug configuration

Use a new, clearly named opt-in such as DICE_AND_DESTINY_ENABLE_AUTHORITY_TRANSCRIPT=1. Follow the repository’s established pattern: flags must be present before Godot/native authority initialization.

DICE_AND_DESTINY_ENABLE_AUTHORITY_TRANSCRIPT=1 \
DICE_AND_DESTINY_INSPECTOR=1 \
./scripts/godot.sh
  • The normal ./scripts/godot.sh launch must keep omniscient recording and UI disabled.
  • Learned battles and D100 battles started in the opted-in process must both write records.
  • Rematches receive distinct battle IDs and clear UI grouping without truncating prior records.
  • The path must remain beneath the current workspace runtime and uncommitted.
  • Never use raw godot --path; follow AGENTS.md.

08 · Tests and acceptance

Prove truth, secrecy, and non-interference

Automated authority tests

  • Transcript disabled writes nothing and produces identical battle results/RNG progression.
  • Human and D100/learned commands identify the correct controller and actor.
  • Automatic events appear even when no command directly represents them.
  • Poison ×2, two actual faces, Antidote, full-status removal, and resulting damage are linked and ordered.
  • Secret defenses and dice are private records first, then one public reveal after both finish.
  • Tip It records the card, die mutation, old/new face, and resulting ability change.
  • Damage records show base, prevention/modification, final amount, and card/health consequences.
  • Normal viewer snapshots/events remain byte-equivalent or semantically equivalent and leak nothing new.
  • Rejected, stale, fabricated, wrong-seat, timeout, and model errors are diagnostic records.

Godot and manual tests

  • Panel exists only in opted-in debug mode.
  • Opening/filtering/copying the panel submits zero gameplay commands.
  • Entries update live during a learned battle and a D100 battle.
  • Hidden entries are unmistakably marked and absent from the normal player log.
  • Public Antidote/status removal is visible in the normal log and complete in the debug transcript.
  • Long battles remain responsive and follow-latest can be paused.
  • Rematch/new battle separation is clear.
  • JSONL can be tailed while playing and parsed after shutdown without partial/corrupt records.

Required verification commands

cd dice-and-destiny-server && go test ./...
cd .. && ./scripts/godot.sh --headless --script res://scripts/verify_battle_authority.gd
./scripts/godot.sh --headless --script res://tests/test_client_logic.gd
./scripts/godot.sh --headless --script res://tests/presentation/verify_battle_scene.gd
./scripts/godot.sh --headless --script res://tests/phase3/verify_learned_battle.gd

Run every additional Godot test through ./scripts/godot.sh and native builds through dice-and-destiny-server/scripts/build_native.sh.

Manual acceptance scenarios

  1. Poison/Antidote: apply Poison ×2, reach Ongoing Effects, observe actual rolls and any Antidote play/removal in both public and developer views.
  2. Secret defense: both actors attack, model defends first, both choose/roll privately, then both defenses and faces reveal together. Confirm the log labels each visibility transition.
  3. Tip It: change a die and resulting ability; confirm the transcript connects card → die → qualification → selected attack.
  4. D100: complete a classic Venom Goblin battle and confirm the same record families work without learned-policy-only assumptions.
  5. Disabled mode: restart normally and confirm there is no panel, omniscient file output, or private-data path.

09 · Definition of done

Completion is an evidence-backed debug workflow

The feature is complete only when an owner can play either supported mode, watch a live transcript, identify every action and automatic consequence—including hidden opponent activity—then open the JSONL afterward and reconstruct the same ordered story, while ordinary gameplay remains viewer-safe and behaviorally unchanged.
  • One common recorder covers learned and D100 authority paths.
  • All required record families have stable typed fields and readable summaries.
  • Visibility is explicit, tested, and never leaked through production/viewer-safe paths.
  • Debug panel and live JSONL are usable throughout a battle.
  • Poison, defense, Tip It, damage, rematch, errors, and disabled-mode acceptance pass.
  • Relevant Phase 1–3, authority, presentation, and client tests remain green.
  • A concise implementation report lists files, schema, flags, output paths, tests, limitations, and manual checklist results.
